# 培养队列与桌宠只读展示

日期：2026-10-27。桌宠 0.2.5 增加正式队列只读展示。下文同时区分可保存、可查询与尚未开放的执行链。

## 已实现的服务端模块

- `TalentPlanService` 保存按 BetterGI 执行目录摘要、一条龙名称隔离的正式队列。最多 32 个角色；每个条目由服务端生成独立随机 ID，记录加入时间、角色编号、等级目标和 A/E/Q 目标。
- 编辑使用 `scopeId + expectedRevision` 条件提交。数据库事务同时保存队列和条目身份；删除保留版本墓碑，退役条目不能在旧回调中复用。大小写不同的配置名使用同一存储键。
- `CharacterPlanService/Targeted.go` 复用已有官方计算器、元素和技能组选择，按明确目标读取或刷新精确请求缓存。普通进度 API 仅使用只读方法，不联网刷新。
- 通用角色等级范围为 1–100，三项天赋目标为 1–10；实际需求计算还受官方角色资料上限约束。实际面板天赋允许命座加成后的数值，不把它静默改成用户目标。
- 计算响应没有官方源时间时，`sourceTime` 保持 null；实际 HTTP 接收时间单独保存为 `fetchedAt`，旧缓存不会补造该值。
- 纯评估器核对角色、条目、目标、来源版本、源时间、获取时间和覆盖范围。只产生连续 FIFO 完成候选；前序角色虚拟预留库存；经过核实的天赋书配方支持绿蓝紫 3:1 合成。只有摩拉 `202` 与智识之冕 `104319` 排除在完成条件之外。

评估函数不联网、不写数据库、不改配置、不启动游戏、不发布完成事件。`ready` 只表示供未来提交器核对的材料候选，不能表示游戏内培养已经执行。

## 网页编辑入口

一条龙配置的“自动秘境”区域增加独立队列编辑器，支持明确选择 UID/区服、添加角色、修改等级和 A/E/Q、调整顺序、删除及读取缓存需求。队列独立即时保存，不占用原一条龙配置的“保存”按钮。

保存失败保留本地草稿；版本冲突需要重新加载后合并，不能自动覆盖服务器的新版本。切换配置或身份时，旧异步响应不能写入新界面。角色绑定缓存失效时仍保留计划，并允许禁用或删减。

已有每日、每周秘境字段及原填充按钮继续使用原逻辑。本阶段的正式队列不会向这些字段写入自动结果。

## API

以下四条路由属于已鉴权的 AutoBGI 网页 API。

| 方法与路径 | 合同 |
| --- | --- |
| `GET /api/talentPlan/config?configName=...` | 返回 `plan`、安全绑定 `roles`、`configAvailable`、`executionAvailable:false` 和警告；读取不创建默认记录 |
| `POST /api/talentPlan/config` | 正文包含 `configName`、读取到的 `scopeId`、`expectedRevision`、`enabled`、`role`、完整 `entries`；返回新版本 |
| `GET /api/talentPlan/characters?uid=...&region=...` | 只读明确身份的缓存面板，返回角色编号、名称、当前等级和三项天赋 |
| `GET /api/talentPlan/progress?configName=...` | 返回计划、纯评估结果和逐条缓存需求；不刷新、不推进 |

新增条目 ID 传空；保留条目 ID 才能修改其目标或顺序；`addedAt` 不可由客户端传入。每个 `targetTalents` 必须恰好三个整数。正文限制 64 KiB，拒绝未知字段、重复字段、重复查询项、多个 JSON 对象及过深嵌套。版本或执行目录变化返回 409，不能自动重放编辑。

2026-10-28 补充可选 `targetSkills:{element,skillIds}`，以及仅用于新选择或再次确认的临时 `skillSelectionFingerprint`。已有绑定随普通保存完整往返，保留条目 ID 时不能清空。角色列表只读返回当前元素的实际技能候选，另有 `POST /api/talentPlan/skill-options/refresh` 显式刷新公开元数据；正文仅包含已保存的配置、目录和版本。网页逐项选择 A/E/Q 后再次核对，最终确认才保存。需求读取、需求刷新和采集准备都使用相同的已保存技能身份；完整来源、失配及兼容规则见 `skill-selection-2026-10-28.md`。此变化不向桌宠旧严格 DTO 追加字段，也不开放生产执行。

`owned`、`missing` 在库存归属尚未核验时返回 null，不能通过把“当前选中角色”附到无身份扫描上变成已知数量。缓存需求可单独展示，但不会使 `applyAllowed` 变成 true。

## 桌宠独立只读合同

实际提供器实现可选 `CultivationQueueReader` 时，`/api/desktop-pet/v1/capabilities` 返回 `features.cultivationQueue:true`。客户端仅在此能力明确声明后显示“已保存培养队列”，复用现有连接和 `apiKey`，不会增加另一套轮询。

`GET /api/desktop-pet/v1/cultivation-queue?presetId=...` 只接受服务端 `/task-presets` 发布的真实 ID，不接受配置名称、路径、`accountId`、`queryRoleId` 或扫描档案选择器。未知及重复查询项返回 400。提供器使用队列与执行目录锁生成一致快照；协议服务在读取前后核对目录摘要、完整预设版本和提供器返回范围，变化返回 409。

结果包含固定 `schemaVersion:1`、实际 `instanceId`、`scope:"instance-config-queue"`、预设身份、执行目录摘要、计划和保存顺序。`plan.revision` 使用十进制字符串，超过 JavaScript 安全整数范围仍保持精确。逐项返回稳定 ID、明确等级及 A/E/Q、可选实际面板、精确目标缓存需求、来源和真实时间。实际面板天赋保留命座加成后的值；没有来源时间或库存时保持 null。面板已经达标仅是一种需求来源，不代表已执行或已从队列移除。

状态仅为 `empty`、`disabled`、`blocked`，三个执行标志 `executionAvailable`、`completionEventsAvailable`、`inventoryVerified` 均为 false。队首是第一个保存条目，不是当前执行任务。服务器和客户端分别校验 32 条角色、每条 128 项材料、真实身份和时间关系、JavaScript 安全数量、未知库存及能力合同。协议 Schema 与合成示例位于 `docs/contracts/`。

桌宠需要先手动读取配置列表并选择预设，不猜默认项。查询角色选择不影响正式队列绑定。网络错误保留同一上下文的历史结果并标记过期；连接、实例、配置和暂停周期变更使迟到回包失效，服务层还会独立复核。此入口不执行保存、远程刷新、背包扫描或游戏控制。

## 已保存技能目标的第二版只读协议

2026-10-28：服务端新增独立可选 `CultivationQueueV2Reader`。`features.cultivationQueueSkillTargets:true` 只声明第二版读取能力，客户端仍独立要求原有 `cultivationQueue:true`。旧查询、旧 DTO、第一版 Schema 和示例保持原合同；显式 `GET /api/desktop-pet/v1/cultivation-queue?presetId=...&schemaVersion=2` 才返回 schema 2。只接受两个规范原始参数各一次，顺序可互换；不能提交 `schemaVersion=1`、其他版本、编码别名或重复项。服务未实现第二版返回 501。

第二版保留原字段、FIFO 顺序、大版本字符串、原始时间和所有未知值，并为每项新增必须出现的 `targetSkills`。真正旧未绑定条目返回 `null`；已绑定条目返回 `{"element":"anemo","skillIds":[101,102,103]}`。元素仅为七种规范小写名称，三个实际技能编号必须互异、为正且不超过 JavaScript 安全整数，按已保存 A/E/Q 次序展示。损坏的部分绑定不静默转为未绑定，而由协议校验拒绝。

宿主只在一次队列与目录锁范围内读取正式进度视图，并从同一视图投影旧字段和绑定。服务端另行复核预设白名单、内容版本及执行目录。绑定不携带候选、临时选择摘要、推测技能名或可信来源证明，不推断当前基础面板或执行授权；`executionAvailable`、`completionEventsAvailable`、`inventoryVerified` 始终为 false。

桌宠沿用 `ReadCultivationQueue` 和现有手动读取入口。请求时冻结预期版本，服务层及界面分别拒绝 v1→v2 和 v2→v1 不匹配，不回退、不丢字段、不改版本号。能力改变会作废在途请求和旧上下文；同一上下文的读取失败仍保留历史并标记过期。显示以已接纳结果为准：schema 1 为“技能绑定未知 · 旧服务未提供”，schema 2 的显式 null 为“旧计划尚未绑定技能”，绑定对象为保存元素与原始 A/E/Q 编号。

独立机器合同与合成示例为 `contracts/cultivation-queue-v2.schema.json`、`contracts/cultivation-queue-v2.example.json`，不替换第一版。此阶段只更新源码、生成绑定和临时验证构建，冻结 0.2.14 发布程序与便携包保持原样；验证范围见 `queue-skill-projection-2026-10-28.md`。

## 配置生命周期

配套服务端现已增加数据库与配置文件之间的持久生命周期意图。带条目的配置可以改名并保留队列身份、顺序及目标；删除时退役条目，并把原配置移至本地恢复归档。源、目标有未完成操作时保持名称占用，不能读取为空队列或覆盖。目标已有文件或活跃计划时仍拒绝覆盖。

队列 API 和一条龙文件创建、保存、改名、删除共用生命周期锁；配置重载使用执行目录写锁。一次临界操作期间目录不变化，避免检查目录 B 的队列却修改目录 A 的文件。

服务启动及显式恢复 POST 可以继续未完成操作，GET 只读。文件被外部修改时保留现场；网页保留失败草稿，不自动重放原写入。完整恢复矩阵、Windows 文件边界、验证和归档位置见 `configuration-lifecycle.md`。这份配置事务尚未包含原生进程派发。

## 未开放的执行链

当前 `ProviderVerified=false`、`executionAvailable=false`。以下仍需开发与验证：

1. 由真实生产者提供明确 UID/区服、扫描批次、实际源时间、完成标记、材料覆盖与质量的可信库存。
2. 一条龙启动前冻结准备、每日字段条件写入及恢复、单次派发后的队列事务提交、故障恢复。
3. 去重的角色完成与全部完成事件；全部完成仍启动原一条龙。
4. 在真实完成生产者就绪后，独立协商培养完成事件及桌宠去重通知；当前只读队列接口不发布事件。

旧桌宠 `/cultivation-plans` 的 `queueAvailable` 和 `completionEventsAvailable` 继续保持 false，旧事件流不会新增未经协商的培养事件。正常空队列不会被当成“全部完成”。

2026-10-28 已补充服务端持久启动状态机、每日字段纯补丁、一次派发协调和内部 outbox，并以合成来源验证失败边界。安全单次入口实际接入来源缺席时的原配置回退；0.2.7 进一步接入独立材料事件历史与补偿，见 `materials-events.md`。生产可信库存、Windows 配置写入和恢复界面仍未开放，上述清单不能整体标为完成。完整合同见 `cultivation-startup.md`。

## 0.2.5 只读展示验证

服务端独立协议 9 个测试、64 个叶场景通过 race；客户端适配器和服务各 6 组、每组重复五次通过 race；真实 Vue 组件 26 项通过，无跳过。实际根模块 Gin 与桌宠 PetV1Adapter 的 HTTP 联通以隔离 SQLite 和合成缓存验证，race 重复三次，覆盖三个文件白名单预设、五种需求状态、精确大版本、未知库存、空及停用队列；读取后无队列变更或游戏派发。

JSON Schema 通过元结构、13 个合法响应、44 个非法变体和 3005 个十进制版本边界验证，真实 Gin 响应也通过。静态检查、TypeScript 与 84 模块 Vite 生产构建成功，最终生成 Windows 0.2.5。详细范围、尚未进行的原生验收和临时文件清理状态见 `acceptance.md`。
