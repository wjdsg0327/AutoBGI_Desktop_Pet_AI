# 跨次库存资源预留设计

日期：2026-10-28。状态：**设计待实现，未经运行验证，不代表库存执行能力已经完成。**

本文记录后续材料执行链所需的持久资源预留合同。现有库存观察、材料目录、单次评估和启动日志均不能单独替代本设计。不得据此开启生产 `inventoryVerified`、材料执行或完成事件能力。

## 1. 当前问题与范围

`TalentPlanService/evaluate.go` 的 `evaluationAllocate`、`evaluationAllocateRecipe` 只扣减一次评估内部的 `stock`。这能避免同一评估中前后条目重复使用材料，却没有跨计划、跨调用或跨重启的扣账。

`TalentPlanService/start_store.go` 的 `FinalizeStarted` 会在同一事务内移除已满足的连续前缀、退役条目身份、保存事件并释放配置占名。若下一次仍读取原扫描数量，已分配给移除条目的材料会重新出现。启动成功本身也不能证明这些材料已经在游戏内消费。

本设计只定义如何保存、复核和结清资源占用。它不提供可信库存生产者、实际消费证明、自动升级角色或周日秘境映射，也不授权把现有未核验观察改成可信库存。

## 2. 资源与观察身份

每份观察、占用和恢复操作都必须绑定：

- BetterGI 执行范围 `scope`、完整 UID、region。
- 可信生产者身份及其校验合同版本。
- 生产者原始观察 ID、来源版本、原始内容摘要。
- 真实源时间、扫描开始和结束时间、首次接收时间；重新读取的获取时间单独保存。
- 规范化覆盖范围摘要、逐项已知状态和数量摘要。
- 对应启动操作、稳定计划 ID、计划版本、稳定条目 ID、目标及完整候选前缀摘要。

`scope` 用于防止不同执行目录的证据混用，但不同目录可能仍控制同一个游戏账户。若系统允许同一 UID、region 从多个 scope 自动执行，必须另设账户级串行约束；或者在旧范围仍有未解决占用时拒绝切换范围建立新预算。不能因为 scope 改变，就为同一物理库存发放第二份可用数量。

观察真实性必须由宿主内部可信生产者保证。来源 URL、内容摘要、请求 ID、`VerifiedBy` 字符串及客户端布尔值均不能自行证明来源。`CollectionStore.Accept` 当前保存的未核验观察不能直接进入可执行账本。

## 3. 建议持久模型

以下名称是拟议名称，尚未建立表或执行迁移。

| 模型 | 主要职责与约束 |
| --- | --- |
| `TalentInventoryLedgerHead` | 资源身份唯一；保存 `scope+UID+region`、CAS 版本、当前可信观察 ID、正常或待核对状态。所有计划共享同一账户预算。 |
| `TalentInventoryObservation` | 不可变保存可信观察合同、原始观察身份、源时间和扫描区间、覆盖及数量摘要、有界快照。拒绝同一观察被改写或旧观察重放成新预算。 |
| `TalentInventoryReservation` | 以 `OperationID` 唯一关联启动；保存账户、观察、计划和候选前缀绑定，以及有界、排序的逐条目原料扣减与摘要。另存占用阶段、结清证据和版本。 |

占用可使用有界 JSON 保存逐条目原料明细，先在 SQLite 查询中限制正文尺寸，再严格解码；或使用受限明细表。选择 JSON 时，必须限制账户未解决占用数量、总材料项数与正文总量，并在事务内逐项核验、使用检查溢出的整数加减。

有效占用状态可区分 `held`、`uncertain`、`committed`；已明确撤销为 `released`，消费或重新观察后结清为 `settled`。启动状态 `finalized` 和占用状态 `settled` 是两回事。保留已结清身份与防重放水位，不以物理删除记录重新获得预算。

## 4. 分配必须记录原料

实际可用数量为可信观察中的明确数量，减去同一资源账户下所有有效占用。材料缺席、未知数量或未覆盖，仍然是未知；不能补零。减法得到负数代表观察与占用需要核对，不能截成零后继续授权。

应由纯分配器产生内部原料追踪，记录每条目、每个真实材料 ID 在分配前后的数量差，再把候选连续前缀的差额冻结到私有启动正文中。

不能使用公开 `MaterialEvaluation.Required` 或折算后的 `Owned` 反推原料占用。例如 8 本绿书加 1 本蓝书满足 1 本紫书时，实际占用为 6 本绿书和 1 本蓝书，另有 2 本绿书剩余。登记 1 本紫书或扣掉全部 8 本绿书都不准确。

只持久化 `CompletedPrefix` 的实际原料扣减。缺料头、waiting 条目及后续展示评估中的虚拟扣减不落库；现有规则没有定义跨计划等待优先级，不应在本设计中隐式引入。摩拉和智识之冕继续按明确材料 ID 排除，不建立资源占用。

## 5. 启动事务边界

| 阶段 | 所需库存动作 |
| --- | --- |
| `PrepareStart` | 在事务外取得可信来源，通过短只读事务取得账本版本和有效占用；以扣账后的数量评估，冻结原始观察、占用视图、真实原料分配及计划依据。此时不登记占用。 |
| `StageStart` | 在现有数据库写事务中取得资源头写锁，复核相同观察、账本版本、计划和分配；原子创建 prepared 启动记录、held 占用并推进账本版本。成功前不允许应用配置补丁。 |
| `BeginCommit` | 在事务内复核自身占用、当前观察、真实时效、计划及宿主已确认的文件边界；原子写入 dispatching 与 uncertain，再允许调用执行器。 |
| `MarkDispatched` | 明确派发成功后登记 dispatched 与 committed。材料仍被占用。 |
| `FinalizeStarted` | 保持队列 CAS、条目退役、事件与启动终态原子提交；有效占用继续保存，释放配置 `ActiveKey` 不释放库存。 |
| `Abort` | 只有宿主可靠证明未派发且配置已经妥善处理时，才原子写 aborted、released 并推进账本版本。 |

`StageStart` 的重复调用要核对已登记的完整占用，不能再次扣账。两个计划同时从同一账本版本准备时，只允许一个成功登记，另一个必须重新准备；不能静默改变已经展示和冻结的候选前缀。

`BeginCommit` 需要核对自身占用和当前基线是否仍有效。其他计划合法登记占用会推进账本版本，但不能仅因版本发生这种变化就误判自身分配失效；自身占用不能被删除、改写或绕过。

私有冻结正文必须绑定资源账户、观察、分配和证明类型，并采用新的明确 schema。恢复读取需要核对这些字段，不能依赖公开评估指纹证明来源。旧材料启动记录没有预留字段时，不能默认它从未使用资源；存在无法解释的历史状态时，应要求重新核对。

## 6. 新观察与释放证据

新请求 ID、新来源版本、较新的获取时间或重新读取同一响应，都不自动释放占用或增加预算。新观察接入时继续扣除未解决占用，材料未覆盖或未知也不会取消原有占用。

允许结清的边界分为：

1. **证明从未派发。** prepared 记录的宿主控制链能证明执行器未调用，或者有与本次操作绑定的可靠 `NotDispatched` 证据，并已核对配置恢复，可释放回原库存基线。
2. **已经派发或 finalized。** 需要与账户、角色、原目标匹配的真实消费证明或可信基础面板达标证明，同时取得晚于该证明且覆盖相关全部原料 ID 的可信实际库存观察。在同一账户事务中采纳新基线并结清对应旧占用，不能先把数量归还旧扫描。
3. **证据不完整或相互冲突。** 保留占用并将资源账本置为待核对，禁止新的材料授权。数量减少本身不能归因到某个角色，单独的面板时间或流程结束也不能证明应释放多少材料。

如果只取得明确消费回执但没有可安全接续的新库存基线，最小实现仍保留原占用，不能凭回执清空占用后继续使用旧基线。

超时、进程退出、正常启动响应、事件送达、扫描过期、计划清空、删除、改名和角色切换都不属于释放证据。尤其不能通过生命周期级联删除占用；稳定计划与条目身份仍用于解释移除后的预留归属。

## 7. 重启与防重放

所有有效占用在重启后继续生效。dispatching 仍表示可能已经派发，不根据超时或当前进程状态自动取消、出队或重发。

恢复必须核对原启动记录、观察、分配摘要及占用状态，查询或重复确认不生成新占用。未知 schema、损坏正文、重复或冲突观察、数量溢出以及无法解释的历史材料日志均保守拒绝。

新观察的晋升、旧观察的防重放水位和占用结清必须同事务提交。不能先结清再更新基线，也不能靠更换请求 ID、计划名或连接范围重放旧数量。

## 8. 无需库存的独立面板路径

`EvaluationInput.Mode="panel-targets"` 的内部评估和启动持久化已另行实现，详见 `panel-targets-2026-10-28.md`。该模式使用独立可信面板证明，明确绑定稳定条目、角色、等级、基础 A/E/Q、技能 ID、元素、UID、region、scope、来源及原始时间。仅当全部条目实际达到全部目标时，可不读取库存或配方，不建立库存观察或占用，每日补丁必须为空；生产来源与目标技能选择仍未接通。

该路径仍需完整计划和文件核对、Stage、Begin、执行器派发确认与 Finalize 事务。它不能把库存 `Verified` 置真，也不能接收面板与材料输入混合后择一放行。

现有 `CharacterPlanService/Targeted.go` 的 `panel-already-met` 是本地缓存结论。缓存 `UpdatedAt`、缺失的官方来源时间和可能包含命座加成的技能等级，不能自动变成可信基础天赋证据。

本设计不要求本轮扩展混合队列的部分前缀；完整的材料预留实现需单独验证。摩拉或智识之冕被排除，也不等于角色面板已达到目标，不能借此伪造面板证明。

建议新增：

- `models/TalentInventoryLedgerModel.go`：上述持久模型及约束。
- `TalentPlanService/reservation_types.go`：资源、观察、分配与状态合同。

必要接线点为 `models/InitDB.go`、`start_types.go`、`start_prepare.go`、`start_validate.go`、`start_store.go`。`store.go` 与文件生命周期保持对未决启动的现有守卫，不能因计划删除或改绑级联清账。生产能力必须等可信生产者、预留、派发和结清链全部满足后另行启用。

未来隔离验收至少覆盖：同一扫描连续两次分配、跨计划并发登记、重启后占用、阶段故障回滚、重复 Stage/Finalize/Abort、防止旧观察换 ID 重放、新扫描仍有未知材料、原料合成扣减、账本负余额、无派发证明不得释放，以及纯面板模式完全不依赖库存。

上述库存账本项目均为待实现、待验证条件；面板路径的独立实现和验证不改变这一状态。本设计文档没有运行测试、迁移数据库、访问实际账户库存或证明 M4 材料执行完成。
